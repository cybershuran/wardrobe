# 衣橱 · 产品设计文档

> 版本 v2 · 2026-08-05 · 目标：从「能用的原型」到「每条旅程都丝滑的成熟产品」

## 1. 产品定位

个人电子衣橱：极简画廊风格的展示页 + AI 服装识别/重绘管线。
两种使用形态：

- **线上版**（GitHub Pages）：纯静态，浏览 + OUTFIT + AI 搭配（用户自填 Key）。
- **本地版**（双击启动）：全功能 —— 浏览、AI 搭配（免填 Key）、管理台（上传识别入库 / 删除 / 重绘）。

## 2. 用户旅程地图

| # | 旅程 | 现状痛点 | 目标体验 |
|---|------|---------|---------|
| J1 | 浏览衣橱 / 看详情 / 筛选分类 | 已可用 | 保持，零改动 |
| J2 | 勾选单品 → 保存 OUTFIT | 已可用 | 保持 |
| J3 | AI 搭配 | 本地版依赖独立代理进程（8643），代理挂了只剩谜之报错 | 本地版与站点同源，进程在则功能在；失败信息可读 |
| J4 | 管理台（上传自拍→识别→入库） | 独立进程（8644），挂掉后主页入口变死链（本次事故） | 管理台与站点同源同进程，入口永远有效；管理台有「返回衣橱」 |
| J5 | 启动 / 停止产品 | 三个进程三个端口；重复双击报 Address already in use；某进程死了无感知 | 一个进程一个端口；重复启动安全（检测到已在运行则直接打开浏览器） |

**本次事故根因**：架构把「一个产品」拆成「三个进程」，进程间无健康感知，
入口链接指向一个可能不存在的服务。单进程架构从根上消除这一整类故障。

## 3. 设计原则（延续现有风格）

- **视觉**：黑白灰极简画廊，大写字间距标签、细线分隔、drop-shadow 产品图，不引入新色彩体系。
- **交互**：少即是多 —— 能自动的不提问，能一步到位的不分两步；所有等待都有明确进度文案，所有失败都有人话解释。
- **文案**：中英混排现状保留（WARDROBE / OUTFITS / 管理台）。

## 4. 目标架构

### Before（三进程）

```
衣橱.command ─┬─ http.server :8642  静态站点
              ├─ proxy.py    :8643  AI 代理（CORS 白名单）
              └─ admin_server.py :8644  管理台 + 管理 API
```

任一进程死亡 → 对应旅程断裂，且无任何提示。

### After（单进程）

```
衣橱.command ── serve.py :8642
                 ├─ GET  /              主页（静态）
                 ├─ GET  /admin         管理台页面
                 ├─ GET  /api/health    健康检查（启动器与测试用）
                 ├─ GET  /api/items     单品列表
                 ├─ POST /api/detect    上传识别
                 ├─ POST /api/generate  生成入库
                 ├─ POST /api/remove    删除
                 ├─ POST /api/redraw    重绘
                 ├─ POST /api/ai/*      AI 搭配转发（同源，无需 CORS）
                 └─ GET  /*             静态资源（items.js / images/ …）
```

- **同源即真理**：页面能打开，管理台和 AI 就一定可用；入口链接永不失效。
- **密钥不出服务端**：AI Key 仍由服务端从 `.env` 注入，浏览器零接触。
- **线上版零影响**：GitHub Pages 仍是纯静态 `index.html + items.js + images/`，
  管理台入口与本地 AI 默认值只在 localhost 出现。
- **数据层不变**：`wardrobe.py` 继续作为 items.js 的唯一读写层，CLI 与服务器共用。

### 模块职责

| 文件 | 职责 |
|------|------|
| `scripts/serve.py` | 唯一服务器：路由、静态、管理 API、AI 转发 |
| `scripts/wardrobe.py` | 数据层：items.js / .sources.json 读写 + 生成管线调用（不变） |
| `scripts/kimi_ai.py` | Kimi 桥接：detect / generate（不变） |
| `scripts/dev-server.js` | npm run dev 静态预览（调试用，不含 API） |
| `tests/` | 自动化测试：数据层 + 服务器路由 + 前端语法 |

## 5. 质量保障

- 数据层：items.js 解析 / 字段读取 / 写入往返的单元测试（用临时副本，不碰真实数据）。
- 服务器：起真实实例，逐一验证路由状态码、健康检查、静态服务、路径穿越防护。
- 前端：node 语法检查 index.html / 管理台内联脚本。
- 验收：测试全绿 + 手动走完 J1–J5 五条旅程。

## 6. v2.1 补丁：启动路径鲁棒性（2026-08-05）

v2 单进程架构消除了「入口指向已死服务」，但走查发现启动路径上仍有三种
「管理台打不开」的故障形态，本补丁逐一消除：

| 故障形态 | 根因 | 修复 |
|---------|------|------|
| 双击后浏览器打开的是旧服务，`/admin` 404 | 端口被没退干净的旧进程（如裸 `http.server`）占用；旧启动器只看「端口有没有人应答」，把死服务当成「已在运行」 | 健康检查携带服务身份（`service:"wardrobe"` + version + pid）；启动器只认「自己人」，发现自家残留（serve.py / http.server）自动清理后重启，陌生程序占用则明示不擅杀 |
| 启动失败只剩一屏 traceback（或窗口一闪而过） | 端口冲突时 serve.py 直接抛 OSError | serve.py 捕获后输出人话提示并以退出码 2 退出；启动器等待就绪失败时在窗口留下排查指引 |
| 双击 `index.html`（file://）打开时根本没有管理台入口 | `isLocal()` 只看 hostname，file:// 被判成「线上」 | `/api/health` 放行 CORS；页面在 file:// 下短超时探测本地服务，探测到「自己人」才补上管理台入口、AI 默认走本机转发；探测不到保持纯线上形态，不会出现死链 |

设计原则不变：**入口只在「确认有效」时出现** —— 宁可不显示，不可显示死链。

配套测试（23 个全绿）新增：健康检查身份与 CORS、端口被占时优雅失败、
file:// 探测逻辑存在性、启动器身份校验与残留清理逻辑。
